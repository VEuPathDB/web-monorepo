# rnaseq-rc Upload Contract

**Date:** 2026-07-30
**Status:** Agreed, not yet implemented

The interface between the `web-monorepo` upload form and the
`vdi-plugin-wrangler` rnaseq-rc importer. This document is the single source of
truth for both sides; neither implementation spec may restate these rules, only
reference them.

Implementation specs:

- [Spec A — web-monorepo](2026-07-30-rnaseq-rc-multipart-upload-design.md) (producer)
- [Spec B — vdi-plugin-wrangler](2026-07-30-rnaseq-rc-wrangler-manifest-design.md) (consumer)

## Why this contract exists

Two independently-designed approaches met in the middle:

- The plugin was engineered around **fixed filename stems** (`sense-counts`,
  `antisense-counts`, `unstranded-counts`, `sample-info`).
- The upload form was engineered around a **manifest file** naming each file's
  role.

The manifest approach wins, on one condition: **the UI generates the manifest,
never the user.** Requiring a hand-written manifest would be strictly worse than
fixed names. Given a UI-generated manifest, it is better than fixed names,
because users' original filenames survive into our system for traceability.

## Transport

Uploads are sent as **3–4 separate `dataFile` multipart parts**, not as a
client-built archive.

VDI packs them server-side. From
`vdi-service/project/core/module/rest-service/.../upload-common.kt:217-233`:

```kotlin
val sizes = if (uploadRefs.data.size == 1) {
  uploadRefs.data[0].repack(...)          // single file: unzip+recompress, or raw→zip
} else {
  uploadRefs.data.pack(into = archive)    // multiple: flat zip
}
```

`pack()` → `Path.compress()` writes `ZipEntry(file.name)` — basenames only, flat,
no subdirectories. The archive the plugin receives is therefore structurally
identical to a client-built zip, and the plugin needs no transport awareness.

`DatasetPostRequestBody.dataFile` is declared `file[]` in
`vdi-service/.../api-schema/types/library.raml:676`, and the frontend's
multipart layer already emits one repeated `dataFile` part per file with its own
filename (`VdiService.ts:465-478`).

### Consequence: validation strictness differs

The multi-file path skips `validateZip`, which is where VDI performs **per-file**
extension and per-file `maxFileSize` checks. Multi-part uploads get only:

- `verifyFileExtensions` — lenient; passes if **any** file matches an allowed
  extension (`upload-common.kt:60-83`)
- total upload size and user quota

Per-file extension validation must therefore be enforced client-side. It is not
a regression to worry about — the plugin re-validates everything — but the form
is now the first line of defence rather than the second.

## The file set

| Role          | Filename          | Origin                           |
| ------------- | ----------------- | -------------------------------- |
| `sense`       | user's own        | user, name preserved             |
| `antisense`   | user's own        | user, name preserved             |
| `unstranded`  | user's own        | user, name preserved             |
| `sample-info` | `sample-info.txt` | generated from the form textarea |
| —             | `manifest.tsv`    | generated by the form            |

Either exactly `sense` + `antisense` (a stranded pair), or exactly `unstranded`.
Never both styles, never a lone `sense` or `antisense`. Always `sample-info` and
always `manifest.tsv`.

## `manifest.tsv`

Always present, **including the unstranded case**. The prototype only emitted a
manifest when an antisense file existed; making it unconditional means the plugin
has exactly one resolution mechanism and no fallback path.

```
sense<TAB>my_counts_sense.tsv
antisense<TAB>my_counts_anti.tsv
sample-info<TAB>sample-info.txt
```

Unstranded:

```
unstranded<TAB>HTSeq_output_2024.txt
sample-info<TAB>sample-info.txt
```

Rules:

- **No header row.** Keeps R-side parsing trivial and avoids a reserved-role clash.
- **Role first, filename second.** Parse on the **first** tab only; everything
  after it is the filename verbatim. Role-first keeps the variable-length,
  user-controlled value last.
- UTF-8, LF line endings, trailing newline.
- One line per file. Every data file in the archive is listed, including the
  generated `sample-info.txt`. The manifest does not list itself.
- Roles are exactly `sense`, `antisense`, `unstranded`, `sample-info`. No
  duplicates.

Listing `sample-info` — even though it is generated and could have been located
by fixed name — buys two things: the plugin has one lookup mechanism instead of
two, and the "reject unreferenced files" rule reduces to _every file but the
manifest must be listed_, one exception rather than two.

### Why a file rather than dataset metadata

Routing roles through `vdi-meta.json` would avoid the extra file, but that is
VDI-owned metadata derived from the `details` multipart field, whose schema is
`additionalProperties: false`. It would require a cross-team VDI change. The
manifest is self-contained between form and plugin.

## Accepted extensions

`.txt`, `.tsv`, `.csv`, `.tab` — case-insensitive, on **both** sides.

This is the union of the two lists that disagreed. Before this contract, the form
accepted `.tsv,.tab,.txt` while the plugin matched `\.(txt|tsv|csv)$`, so `.tab`
passed the form and was rejected by the plugin, and `.csv` was accepted by the
plugin but unselectable in the form. Widening costs nothing because the plugin
sniffs the delimiter from file content rather than trusting the extension.

VDI's own `allowedFileExtensions` is a third list, and it rejects at upload time
before the plugin runs, so it must include all four. **Done** — widened in
`webservices-quadlets` commit `2219913` (`vdi/config/config.yml`, branch
`rnaseq-rc`).

## `sample-info` size limit

**100,000 UTF-8 bytes.**

The plugin enforces this at `counts_files.R:126` using
`nchar(sample_info_text, type = "bytes")`, deliberately and with a documented
rationale (encoding-independence, and a conservative proxy for token cost). That
measure is correct and stays.

The form must therefore measure the same way:

```ts
new Blob([text]).size; // UTF-8 byte length
```

**Not** `String.prototype.length`, which counts UTF-16 code units. The three
candidate measures — UTF-8 bytes, UTF-16 code units, and Unicode code points —
coincide only for ASCII. A French or CJK Methods section could otherwise pass the
form and be rejected by the plugin after upload.

`Blob` rather than the more obvious `new TextEncoder().encode(text).length`
because **jsdom does not provide `TextEncoder`**, so the latter passes in a
browser and throws in jest. Verified empirically: `Blob` gives 2 for `é`, 5 for
`hello`, 9 for `日本語`, and works in both environments with no polyfill. It is
also the same primitive the `File` constructor uses, so it cannot disagree with
the bytes actually uploaded.

## Filename collisions

Filenames within one upload must be unique. VDI copies every part into one flat
temp directory (`upload-common.kt:157`):

```kotlin
map { it.copyTo(tmpDir.resolve(it.name).toFile()) }
```

Kotlin's `copyTo` defaults to `overwrite = false`, so a duplicate name throws
`FileAlreadyExistsException`, which propagates to JAX-RS as an **opaque 500** —
not silent data loss, but not a usable error message either.

Two distinct cases, handled differently:

**Generated-vs-user — generated files yield, silently.** A user's count file may
legitimately be named `sample-info.txt` or `manifest.tsv`; the plugin's current
documentation instructs users to name files exactly that way, so such files exist
on disk today. Because the manifest carries the name→role mapping, generated
filenames are not load-bearing — nothing requires `sample-info.txt` to be called
that. The form renames **its own** generated file on collision
(`sample-info-1.txt`, and so on). The user sees no error and their original
filename survives, which is the whole point of the manifest.

**User-vs-user — reject with a clear message.** Two count files sharing a
basename (`run1/counts.tsv` and `run2/counts.tsv` both arrive as `counts.tsv`)
is a realistic stranded-pair mistake. Both names are user-owned and both should
be preserved, so this is a form-level validation error: _your two count files
have the same name; please rename one._

**Tabs in filenames** are rejected. Legal on Linux, and they would break the
manifest parse.

## Filename sanitization ordering

`sanitizeFileName` (`Service/utils/sanitization.ts`) replaces whitespace with
underscores. It currently runs in `create-dataset.ts:66`, i.e. **after** files are
assembled.

That is harmless today, because the client builds the zip and JSZip preserves
inner entry names — only the outer zip gets renamed, so the manifest matches.
Once files become individual parts, a manifest written before sanitization would
reference `my counts sense.tsv` while the archive contains
`my_counts_sense.tsv`, and the plugin's sense/antisense mapping would break
silently.

**Sanitization must move to the input boundary**, so filenames are canonical
before the manifest is written and the displayed filename matches what is
uploaded. "Original filename" therefore means _whitespace-normalised original_;
that is an accepted, documented loss.

## The type name is `rnaseqrc`, not `rnaseq-rc`

**No hyphen.** This is the canonical spelling everywhere: VDI config, the
frontend's `implementedUploadTypes`, the plugin's `wrangle-<name>.R` script, and
the plugin's fixture `vdi-meta.json` files.

The type was originally built as `rnaseq-rc` in both the frontend and the
wrangler plugin, and VDI config was normalised to `rnaseqrc` in
`webservices-quadlets` commit `62f6cdb` ("remove hyphen"). All nine other
registered types are single unseparated lowercase words — `bigwigfiles`, `biom`,
`genelist`, `lightweight`, `rnaseq`, `phenotype`, `isasimple`, `stf` — so the
hyphen was the outlier. Nothing technically forbids one (`DataType.of()` only
lowercases, and the config schema puts no `pattern` on `name`), but a 9/9
convention was judged worth keeping over a cheaper one-line revert.

**The name is load-bearing, not cosmetic.** `bin/wrangle.R:63` in the plugin
interpolates it straight into a filename:

```r
script_path <- file.path("lib/R", paste0("wrangle-", datatype, ".R"))
```

A mismatch therefore fails with _"The data type 'X' is not supported by this
plugin"_ rather than anything diagnostic. Spec A renames the frontend constant;
Spec B renames the script and its fixtures.

Users never see this string — the user-facing label is `category`, "RNA-Seq raw
counts".

## Deployment prerequisite — satisfied

Spec A removes the prototype `rnaseq-rc` → `rnaseq` type aliasing from both sites
that carry it — `UploadFormController.tsx:143-147`, and **two** separate sites in
`DatasetTypeConfig.ts`: `filterAvailableDataTypes` (86-92) and `promoteTypeConfig`
(55-57). The second was missed during design and only surfaced in review; note it
aliased to `rnaseq`, a _different_ pre-existing dataset type, so it would have
misrouted rather than merely mismatched.
After that, `rnaseqrc:1.0` must be registered in VDI's stack config as a real
plugin data type, because:

- `filterAvailableDataTypes` hides the type from the upload menu when VDI does
  not report it, and
- `PluginRegistry.require()` throws for unregistered types,

so a premature merge would break uploads rather than merely hide the form.

**This is now done** — registered at `vdi/config/config.yml:148` in
`webservices-quadlets` (branch `rnaseq-rc`), pointing at the `wrangler:80` plugin
server. `rnaseq:1.0` (normalized counts, `rnaseq:80`) and `rnaseqrc:1.0` (raw
counts, `wrangler:80`) are separate plugin servers with distinct categories, and
coexist indefinitely by design.

Remaining gate: that branch must be merged and deployed before Spec A merges.
